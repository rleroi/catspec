Your spec is the source.
The LLM is the compiler.

CaT is a human-readable specification format and toolchain for defining full-stack applications. Specs are plain .md files in bacon/ — frontmatter, headings, tables, fenced code, all rendered natively by GitHub and every editor. Anything binding is just a sentence with RFC 2119 MUST/SHOULD/MAY in it, wherever it's relevant.

Why CaT exists

Traditional codebases are optimized for compilers, not comprehension. LLMs work best with structured natural language. CaT makes the human-readable spec the single source of truth and treats generated code as a derived, regenerable artifact.

Spec is the source

Humans edit bacon/*.md. Code in src/ is generated, reviewed, and merged via PR.

Progressive specificity

Start vague (“I need auth”). Add detail only where it matters. The LLM fills the rest.

Provider binding

using: Supabase Auth tells the compiler which off-the-shelf tools to wire up idiomatically.

Git-native

Push to bacon/, CI transpiles, opens a PR. Humans review the diff before merge.

The spectrum of control

CaT’s core idea: one document, five levels of authority. Higher levels override lower ones.

Intent
“I need auth”
Provider, flows, UI, all code
Strategy
using: Supabase Auth
Wiring, components, error handling
Behavior
Flows, Views, Models
Implementation code
Pin
A sentence with MUST/SHOULD, anywhere
Everything else
Literal
A fenced code block, anywhere
Nothing — hands off

Specificity hierarchy: Fenced code > MUST/SHOULD/MAY > Flow/View > description text > LLM discretion.

“Pin” and “Literal” are properties of a sentence or a block, not containers you put things in. Write MUST/SHOULD/MAY (RFC 2119) in the middle of a normal paragraph and it's binding right there. Fence a code block and it's verbatim right there. No dedicated section required to make either one count.

Built on familiar ideas

CaT specs are plain .md files with nothing bolted on except the four frontmatter fields. Every structural signal below is borrowed directly from a format the model — and the human — has already seen a million times.

Format What CaT borrows Why not the whole thing
Markdown + YAML frontmatter Headings for structure, fenced code for verbatim content, GFM tables for model schemas, frontmatter for the four closed-vocabulary fields (name, stack, feature, using) — adopted directly, this is the entire host format
RFC 2119 MUST / SHOULD / MAY, used inline in ordinary prose — exactly how real RFCs use them, not segregated into a special section — adopted directly, no dedicated heading needed at all
TypeScript / Prisma-style types A model reference is just the other model's name (Profile); a list is Model[] — no reference to / list of phrasing to learn — adopted directly for the Type column in a model table
Gherkin Nothing structural. Flow: steps stay plain numbered prose Full .feature files must contain only Gherkin — no models, no stack. A parallel Given/When/Then syntax alongside numbered steps would just be two ways to write the same thing
RFC 7322 Nothing directly — it's a prose style guide for IETF documents, not a spec language Relevant citation, wrong layer

Why not go all the way to Gherkin .feature files? Cucumber tooling assumes a .feature file contains only scenarios. CaT needs stack binding, provider binding, models, and pins living next to behavior in one readable file. Split those out to stay Cucumber-compatible and you've traded one custom format for three interlinked ones (Gherkin + YAML models + Markdown prose) glued together by a naming convention — the exact problem a unified format was supposed to avoid.

Why plain Markdown? Markdown headings never require a closed vocabulary — an LLM encountering a heading it doesn't recognize just treats it as prose context, not a parse error. Fenced code blocks have an unambiguous end (the closing ```), unlike indentation-based blocks. YAML frontmatter is the one place that does need a closed vocabulary, and YAML already defines that cleanly.

Why not a Pin: or Literal: heading either? Because real specs don't segregate their MUST statements into an appendix — they write “the server MUST respond within 5 seconds” right in the paragraph about server responses. And real Markdown docs don't need a special heading to tell you a fenced code block is verbatim — that's what a fence already means. Both of those signals already existed; wrapping them in a CaT-only heading just added a second thing to learn for no parsing benefit.

Gherkin vs. CaT Flow

The CaT spec language

CaT specs are plain .md files. Frontmatter for the four fields that need a closed vocabulary. Headings for the three structural blocks that map to distinct generated artifacts. GFM tables for model schemas. Fenced code for anything verbatim. RFC 2119 words for anything binding. That's the entire language — nothing else is reserved.

Why this design resolves the usual parsing traps:

• A fenced code block ends at the closing ``` — no ambiguity from blank lines or re-indentation inside the verbatim code. This works for any fenced block, not just a specially-named one.
• An unrecognized heading is never an error. Markdown never promised a closed vocabulary of headings, so the transpiler simply treats anything it doesn't recognize as descriptive prose.
• Frontmatter is the only place with a closed vocabulary (name, stack, feature, using), and YAML already defines exactly how that parses.
• The three structural headings (Model, Flow, View) are matched case-insensitively — LLM-authored specs drift in casing over time, so the grammar doesn't punish it.
• MUST/SHOULD/MAY carry their own meaning wherever they appear — no heading has to exist for a sentence to be binding.
• The file extension is plain .md, not a custom one — what marks a file as a spec is living in bacon/ with name:/feature: frontmatter, not its extension.

Project layout

Every CaT project has a bacon/system.md (required) plus feature and model files. Infrastructure config lives at the project root, outside the spec, as plain files a human can read or tune directly.

my-cat-project/
├── bacon/                  # source of truth, plain .md, 100% human-authored
│   ├── system.md           # required
│   ├── auth.md
│   ├── models.md           # shared models
│   └── features/
│       └── invoices.md
├── cat.config.yaml         # transpiler settings + provider profiles
├── purr                    # machine state: hashes, outputs, deps, last commit
└── src/                    # generated output

cat.config.yaml holds settings a human tunes; purr is a reviewable, diffable record of what the transpiler last did, sitting right next to the config that produced it. Neither belongs inside bacon/: that folder's diffs are supposed to mean “a human changed the spec,” and machine-updated state would make every transpile run look like a spec change too.

Frontmatter — name, stack, feature, using

Every spec file opens with a YAML frontmatter block. These four fields are the entire closed vocabulary in the language — everything else is Markdown. bacon/system.md is a fixed, required filename, so its own name doesn't need to appear in a field — name just holds the app's name.

---
name: FreelanceOS
stack:
  framework:  Next.js (App Router)
  language:   TypeScript
  database:   Supabase
  auth:       Supabase Auth
  styling:    Tailwind + shadcn/ui
  deploy:     Vercel
---

A simple invoicing app for freelancers.

Feature files use feature and using instead. At its simplest, a feature is frontmatter plus one sentence:

---
feature: Authentication
---

Users can sign up and log in.

using binds a feature to a provider profile under the providers: key in cat.config.yaml. It's a YAML list — one or many providers.

---
feature: Invoices
using: [Supabase, Resend]
---

If using is omitted, the LLM chooses a provider based on stack and records the choice in purr.

## Model: and Invariants:

A model heading is followed by a plain GFM table — the same table syntax you'd use in any README. Reference fields use the other model's name directly, the way TypeScript or Prisma would; append [] for a list. Enum values are comma-separated in the Notes column, not pipe-separated, since a literal | would collide with the table's own column delimiter. Shared models referenced by multiple features belong in a dedicated models.md, not inside any one feature file. 

## Model: Invoice

| Field | Type | Notes |
|---|---|---|
| id | uuid | primary key |
| owner | Profile | |
| status | draft, sent, paid | |
| items | LineItem[] | |
| created_at | timestamp | auto |

Invariants:
- The invoice MUST have at least one LineItem when status is "sent".

Types: text, integer, decimal, boolean, date, timestamp (UTC, ISO-8601), uuid, email, url, json, currency (integer minor units + ISO 4217 code), a comma-separated enum, or another model's name (optionally with a trailing []) for a reference.

Notes column: free text — primary key, nullable, unique, auto, min N, max N, default VALUE, or renamed from Field (signals a rename so incremental transpilation writes a migration instead of dropping and re-adding the column) are common, but this column isn't a closed vocabulary — it's read as prose.

## Flow: and ## View:

A Flow body is numbered steps — one way to write it, no alternative syntax to choose between. A View has no steps at all — it's a layout/data description. Conditions and failure handling are just more prose, phrased however reads naturally — there's no reserved marker for them, so “if X fails, do Y” and “on failure, do Y” are equally valid.

## Flow: Send Invoice

1. User clicks “Send” on a draft invoice with all required fields filled in
2. System generates a PDF and emails it to client_email
3. Invoice status changes to "sent"

If the client has a Stripe payment method on file, include a payment link.
If sending the email fails, show “Failed to send email” and keep
the status as "draft".

## View: Dashboard

Show tasks grouped by status in a kanban board.
Filter by assignee and priority.

Prefer describing the triggering action rather than a step number ("if sending the email fails", not "if step 2 fails") — numbered-step references break silently when someone inserts a step earlier in the flow.

Anything binding, anything verbatim

Binding and verbatim are properties, not headings. Both signals already exist in plain Markdown, so CaT just uses them where they occur:

Binding: any sentence containing MUST, SHOULD, or MAY is binding at that severity, wherever it appears — in a feature's description, inside a Flow step, under a View, or grouped under any heading you make up (## Security, ## Performance, whatever reads naturally). The word is the syntax; the heading, if any, is just for humans skimming.

Verbatim: any fenced code block outside a Model's schema table is copied exactly, no modification. The language tag on the fence plus the surrounding prose is enough context for where it goes — no extra heading needed to say "this one's literal," a fence already means that. 

Passwords MUST be at least 12 characters.
All database queries MUST use Row Level Security.
The dashboard SHOULD load in under 1 second with up to 500 tasks.

Validate the session server-side before rendering a protected page:

```typescript
const { data: { session } } = await supabase.auth.getSession()
if (!session) redirect('/login')
```

Scope follows the file: a MUST/SHOULD statement in system.md is global, the same statement in a feature file is local. If both address the same subject, the feature-level statement wins.

References & resolution

Model names (after ## Model:) and feature names (the feature frontmatter value) are globally unique across bacon/, matched by exact, case-sensitive text. Forward references are allowed — a field can have type Team before Team is defined in another file, since the transpiler reads every file before resolving anything.

If a model is referenced by two or more features, move it to models.md. This keeps ownership unambiguous and lets incremental transpilation track the dependency correctly in purr.

Unrecognized headings never participate in resolution — only frontmatter fields and Type-column values that match another model's name (with or without a trailing []) are looked up against the closed vocabulary.

Config — cat.config.yaml

Controls how the transpiler operates and holds provider profiles. It lives at the project root, as a plain file, because it's infrastructure, not specification. 

# cat.config.yaml
version: 0.1

transpiler:
  model:     claude-sonnet-4
  strategy:  incremental    # or "full"
  output:    src/
  retries:   2              # self-correction attempts on build failure

providers:
  supabase-auth:
    package: "@supabase/supabase-js"
    session: cookies
  resend:
    package: resend

The internal shape of a provider entry isn't part of the closed vocabulary — it's read as context for the transpiler, the same way any other prose in the spec is.

Recognized headings & fields
MarkerScopePurpose
nameFrontmatter, system.md onlyApp name
stackFrontmatter, system.md onlyTechnology choices (framework, database, etc.)
featureFrontmatter, any feature fileCapability name
usingFrontmatter, any feature fileProvider binding
## Model: + tableAny fileData entity

That's the whole closed vocabulary: four frontmatter fields, three headings, one label, two universal signals. Any other heading is organizational prose.

Semantics for the LLM compiler

What each construct means to the transpiler, independent of syntax:

ConstructMeaning
Frontmatter fieldsStructured and authoritative — parse as YAML, values are not up for interpretation
Prose under a headingGuidance — follow the intent, use judgment on implementation
usingYou MUST use these providers; load the provider profile if one exists
Flow steps (numbered)Implement each step; steps describe WHAT happens, you decide HOW
View descriptionGenerate UI matching the description; there is no sequential logic to implement
MUST / SHOULD / MAY, anywhereRFC 2119 severity governs discretion: MUST is non-negotiable, SHOULD is a default you can override with a stated reason, MAY is optional
Fenced code, anywhereVerbatim. Copy exactly, do not modify.
InvariantsImplement as a database constraint, validation rule, or runtime check, scoped to that one model

Specificity hierarchy when things conflict: fenced code > MUST/SHOULD/MAY > Flow/View > description text > LLM discretion.

How transpilation works

Push changes to bacon/. CI reads the diff, calls the LLM transpiler, and opens a PR with generated code. Humans review before merge.

bacon/ changed → git push → GitHub Action → validate → enrich → confirm → transpile → open PR → human review

The purr file

purr, a plain text file at the project root, tracks operational metadata: content hashes, generated output paths, cross-feature dependencies, and the last transpiled commit. Incremental runs diff against it to transpile only what changed. When the LLM makes an implementation choice worth pinning down, it writes it back into the spec as a plain MUST/SHOULD sentence. 

# purr
last_transpiled_commit: a3f7c2e

bacon/auth.md:
  content_hash: a1b2c3d4
  outputs:
    - src/app/(auth)/login/page.tsx
    - src/lib/auth.ts
  dependencies:
    - bacon/models.md

Transpiler phases

1. Validate

Scan all spec files under bacon/. Check for duplicate models, missing references, structural errors.

2. Enrich

Ask clarifying questions. Propose pins for ambiguous decisions. Human approves.

3. Confirm

Present the finalized spec diff. Wait for explicit approval before generating code.

4. Transpile

Generate idiomatic code for the declared stack. Write migrations, components, routes.

Example: FreelanceOS

Three files. Fully readable. Produces a Supabase + Next.js invoicing app.

bacon/system.md

name: FreelanceOS
stack:
  framework:  Next.js (App Router)
  language:   TypeScript
  database:   Supabase
  auth:       Supabase Auth
  styling:    Tailwind + shadcn/ui
  deploy:     Vercel
---

A simple invoicing app for freelancers.
Manage clients, create invoices, track payments.

All database access MUST use Row Level Security.
Users MUST only access their own data.
