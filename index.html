Why CaT exists

Traditional codebases are optimized for compilers, not comprehension. LLMs work best with structured natural language. CaT makes the human-readable spec the single source of truth and treats generated code as a derived artifact — like terraform plan output, but for an entire application.

Spec is the source

Humans edit bacon/*.cat. Code in src/ is generated, reviewed, and merged via PR.

Progressive specificity

Start vague (“I need auth”). Add detail only where it matters. The LLM fills the rest.

Provider binding

using: Supabase Auth tells the compiler which off-the-shelf tools to wire up idiomatically.

Git-native

Push to bacon/, CI transpiles, opens a PR. Humans review the diff before merge.

The spectrum of control

CaT’s core idea: one document, five levels of authority. Higher levels override lower ones.

Intent
“I need auth”
Provider, flows, UI, all code
Strategy
using: Supabase Auth
Wiring, components, error handling
Behavior
Flows, Views, Models
Implementation code
Pin
Hard constraints (MUST)
Everything else
Literal
Verbatim code blocks
Nothing — hands off

Specificity hierarchy: Literal: > Pin: > Flow/View steps > description text > LLM discretion. Pins map to RFC 2119 MUST. Description text is informative guidance.

Built on familiar ideas

CaT is not trying to replace every spec format. It composes ideas that already work — and adds what none of them provide alone: a full-stack, LLM-compilable source of truth with a progressive specificity ladder.

Format What it does well What CaT adds
Gherkin Feature/scenario structure, Given/When/Then, Cucumber ecosystem Stack, models, views, providers, pins, literals, full-stack codegen
OpenAPI Machine-parseable API contracts, tooling, validation UI, data models, auth flows, non-API behavior
GraphQL SDL / Prisma Precise type and schema definitions Behavior, UI, provider wiring, natural-language intent
RFC 2119 MUST / SHOULD / MAY requirement levels Pin: and Constraint: blocks scoped to features
RFC 7322 Structured prose for standards documents Not a prose style guide — a compilable application spec

Why not just Gherkin? Gherkin is optimized for executable acceptance tests. It wants concrete Given/When/Then from the start. CaT wants the opposite: start with one vague line, add rigor only where you care. Gherkin also has no concept of stack, models, provider binding, or “copy this code verbatim.”

Why a unified .cat format? Because the compiler is an LLM, not a deterministic parser. One readable file per feature beats five interlinked formats for v0.1. Export to Gherkin or OpenAPI can come later; the transpiler skill reads raw text today.

Gherkin vs. CaT

Gherkin — test-oriented
Feature: Authentication
  Scenario: Sign up with email
    Given the user is on the sign up page
    When they enter a valid email and password
    Then an auth account is created
    And a verification email is sent
CaT — compile-oriented

The .cat language

Structured text files in bacon/. Readable without tooling. Parseable by any LLM. Indentation-scoped blocks, similar to Python or YAML.

Project layout

Every CaT project has a bacon/system.cat (required) plus feature and model files. Infrastructure config lives in .cat/, outside the spec.

my-cat-project/
├── bacon/                  # source of truth
│   ├── system.cat          # required
│   ├── auth.cat
│   ├── models.cat          # shared models
│   └── features/
│       └── invoices.cat
├── .cat/
│   ├── config.yaml         # transpiler settings
│   ├── purr                # hashes, outputs, deps
│   └── providers/          # provider profiles
└── src/                    # generated output
System: and Stack:

system.cat names the application, describes it in prose, and declares the technology stack.

System: FreelanceOS

A simple invoicing app for freelancers.

Stack:
  framework:  Next.js (App Router)
  language:   TypeScript
  database:   Supabase
  auth:       Supabase Auth
  styling:    Tailwind + shadcn/ui
  deploy:     Vercel
Feature: and using:

A feature is the primary building block. At its simplest, two lines:

Feature: Authentication
  Users can sign up and log in.

using: binds a feature to provider profiles in .cat/providers/. Multiple providers are comma-separated.

Feature: Invoices
  using: Supabase, Resend
Model: and Invariant:

Models define data entities. Shared models referenced by multiple features belong in models.cat.

Model: Invoice
  id:           uuid, primary key
  owner:        reference to Profile
  status:       draft | sent | paid
  created_at:   timestamp, auto

  Invariant: must have at least one LineItem when status is "sent"

Types: text, integer, decimal, boolean, date, timestamp, uuid, email, url, json, currency. Enums use pipe syntax.

Flow: and View:

Flow = numbered sequence of actions. View = page layout and data display (no steps).

Flow: Send Invoice
  1. User clicks send on a draft invoice
  2. System validates required fields
  3. System emails PDF to client_email
  4. Status changes to "sent"

  On failure (step 3):
    Show error, status remains "draft"

View: Dashboard
  Show tasks grouped by status in a kanban board.
  Filter by assignee and priority.
Pin: and Literal:

Pin: = hard constraint (MUST). Literal: = verbatim code, no modifications.

Pin:
  Passwords MUST be at least 12 characters
  Rate limit: 5 attempts per minute per IP

Literal: typescript
  const { data: { session } } = await supabase.auth.getSession()
  if (!session) redirect('/login')
Constraint: and keywords reference

Non-functional requirements at feature or system scope.

Constraint: security
  All database queries MUST use Row Level Security
KeywordPurpose
System: / Stack:App identity and technology (system.cat only)
Feature:Capability declaration
using:Provider binding
Model: / Invariant:Data entities and business rules
Flow: / View:Behavior sequences and UI layout
On failure: / If / WhenError handling and branching

Constraint:Non-functional requirements

How transpilation works

Push changes to bacon/. CI reads the diff, calls the LLM transpiler, and opens a PR with generated code. Humans review before merge.

bacon/ changed → git push → GitHub Action → validate → enrich → confirm → transpile → open PR → human review

The purr file

.cat/purr tracks operational metadata: content hashes, generated output paths, cross-feature dependencies, and the last transpiled commit. Incremental runs diff against it to transpile only what changed. When the LLM makes implementation choices, it writes them back as Pin: blocks in the spec. 

# .cat/purr
last_transpiled_commit: a3f7c2e

bacon/auth.cat:
  content_hash: a1b2c3d4
  outputs:
    - src/app/(auth)/login/page.tsx
    - src/lib/auth.ts
  dependencies:
    - bacon/models.cat

Transpiler phases

1. Validate

Scan all .cat files. Check for duplicate models, missing references, structural errors.

2. Enrich

Ask clarifying questions. Propose pins for ambiguous decisions. Human approves.

3. Confirm

Present the finalized spec diff. Wait for explicit approval before generating code.

4. Transpile

Generate idiomatic code for the declared stack. Write migrations, components, routes.

Example: FreelanceOS

Three files. Fully readable. Produces a Supabase + Next.js invoicing app.

bacon/system.cat

System: FreelanceOS

A simple invoicing app for freelancers.
Manage clients, create invoices, track payments.

Stack:
  framework:  Next.js (App Router)
  language:   TypeScript
  database:   Supabase
  auth:       Supabase Auth
  styling:    Tailwind + shadcn/ui
  deploy:     Vercel

Constraint: security
  All database access MUST use Row Level Security.

bacon/auth.cat

Feature: Authentication
  using: Supabase Auth

  Users can sign up with email or Google OAuth.
  After first login, a Profile is created automatically.

  Model: Profile
    id:           uuid, primary key
    display_name: text
    avatar_url:   text, nullable
    created_at:   timestamp, auto

  Flow: Sign Up
    1. User enters email and password, or clicks "Sign in with Google"
    2. System creates auth account
    3. System sends verification email (email signup only)
    4. On first login, system creates a Profile row

  Flow: Sign In
    1. User enters credentials or uses Google
    2. System redirects to /dashboard

  Pin:
    Passwords MUST be at least 10 characters
    Session duration: 7 days

bacon/features/invoices.cat

Feature: Invoices
  using: Supabase, Resend

  Users can create, edit, send, and track invoices.

  Model: Invoice
    id:           uuid, primary key
    owner:        reference to Profile
    client_name:  text
    client_email: email
    status:       draft | sent | paid | overdue
    due_date:     date
    created_at:   timestamp, auto

  Flow: Send Invoice
    1. User clicks "Send" on a draft invoice
    2. System validates required fields
    3. System generates a PDF
    4. System emails the PDF to client_email
    5. Status changes to "sent"

    On failure (step 4):
      Show error, status remains "draft"

    Pin:
      PDF generation: use @react-pdf/renderer

  View: Dashboard
    Show total outstanding, total paid this month, overdue count.
    List recent invoices with status badges.

Get started

CaT ships as agent skills today. A CLI and GitHub Action are on the roadmap.

Scaffold a project

Install the cat-init skill and ask your agent to initialize a CaT project. It creates the folder layout, system.cat, config, and CI workflow.

# Install skills (when published)
npx skills add cat-hq/catspec

# Or copy from this repo
skills/cat-init/SKILL.md
skills/cat-transpiler/SKILL.md

Transpile

Point your agent at a repo with a bacon/ directory. The cat-transpiler skill runs validate → enrich → confirm → transpile.

Roadmap

  • cat-init skill — scaffold projects interactively
  • cat-transpiler skill — validate, enrich, transpile loop
  • End-to-end POC — full loop on a real Supabase + Next.js project
  • CaT CLI — cat validate, cat transpile, cat diff
  • Provider profiles — Supabase, Stripe, Resend, Clerk
  • GitHub Action — uses: cat-hq/cat-transpile@v1
  • Formal parser — AST, linter, editor support (optional for v0.1)
  • Export adapters — cat export --gherkin, --openapi
